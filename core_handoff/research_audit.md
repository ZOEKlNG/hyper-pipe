# 核模型参考说明审查

**后续核查修正（2026-10-29）：** 本轮3.21.12的`set_bytes(ptr,len)`会构造临时`std::string`，旧计时保留，但载荷复制账本须多计这一层；`mutable_bytes()->assign(...)`可避免它。详见[生成代码/API核查与重测](../stateful_handoff/PROTOBUF_3_21_NOTES.zh-CN.md)。


审查对象：用户本轮粘贴的核模型讨论（`已粘贴的文本.txt`），已完整阅读。本文是源码与语义核查，没有运行性能测试。附件中的纳秒数、倍数、机器码体积、缓存失效惩罚及正常工况百分比均没有可核验的原始记录，不能作为实测结论或预测。

## 关键结论

把采集工作线程与日志线程拆开是合理的设计选项，但不能据此认定“工作线程编码 Protobuf”属于反模式。它把计算放在不同的核，并改变队列元素大小、缓冲区寿命、背压位置和发送方式；是否合适需要同口径实验。DPDK 官方也将完整处理模型与流水线模型作为可选架构讨论。[S10]

附件最主要的问题是复制次数的账本切换了编码器。普通生成代码的 `set_url(ptr, len)` 会把内容放进消息拥有的字符串存储；随后向连续数组序列化又会写出该内容。Arena（区域内存分配器）能改变分配和回收方式，不会自动把这个 setter 变成借用网络缓冲区。[S1–S3]

### 1. 普通生成代码条件下的复制账本

下表仅统计一个变长字段的内容复制，假设三种方案都使用普通拥有式字符串 setter、连续数组序列化，而且 B 的日志线程确实再把队列中的 wire bytes（线格式字节）复制进批次缓冲区。没有计入网卡 DMA、内核或传输后端的复制。

| 方案 | 字段内容路径 | 内容复制次数 |
|---|---|---:|
| A：采集核复制到原生槽位，日志核生成式 PB 编码 | mbuf → Slot → PB 字符串 → BatchFrame | 3 |
| B：采集核生成式 PB 编码，日志核复制已编码字节 | mbuf → PB 字符串 → 队列 wire → BatchFrame | 3 |
| C：传递 mbuf 引用，日志核生成式 PB 编码 | mbuf → PB 字符串 → BatchFrame | 2 |

附件 A 的说明仍写 `tls_event` 和 `SerializeWithCachedSizesToArray`，没有解释如何跳过 Slot → PB 字符串；C 示例则明确调用 `set_url(ptr,85)`。因此表中 A 两次、C 一次不能由所给实现推导出来。它们可以是另一种实现的目标：例如日志核从字段视图直接写线格式，或采用具有明确定义的借用式消息存储。需要将这种实现单独命名、验证和测量，不能把它与普通生成式 PB 混在一列。

B 也不必永远多一次 BatchFrame 复制。使用适当的分散收集发送、独立消息批量发送或直接向最终发送缓冲区编码，可能改变其路径；这取决于后端和缓冲区所有权，应该作为另外的实验配置。`sendmmsg` 批量提交多个报文与把多个消息合并为一个大报文也不是同一个操作。

生成代码的字符串内部表示会随版本和配置变化，不宜把所有版本都断言成特定 `ArenaStringPtr` 布局。这里的关键是拥有式 setter 的 API 语义，而不是内部类名。对固定版本，官方 `ArenaStringPtr::Set(absl::string_view, Arena*)` 的分配/`assign` 实现和数组输出中的 `memcpy` 可直接核验。[S2–S3]

### 2. StringPiece、string_view、Cord 不能互换

`StringPiece` / `string_view`（字符串视图）作为 setter 参数，不等于目标消息借用该地址。必须核对具体 setter 是否复制、字段存储类型以及序列化后端。

官方 C++ 生成代码支持 `absl::Cord` 的范围是单值 `bytes` 字段，包括 oneof 内的单值 bytes；普通 `string`、重复 string、重复 bytes 不支持这种 Cord 配置。因此 URL、Host、Cookie 如果在现有 schema 中是 `string`，不能直接通过一句“使用 Cord”保持同样生成接口并消掉复制。[S1]

`MakeCordFromExternal` 确实允许引用外部存储，但官方契约要求这些字节在 Cord 的生命期内不被修改，并一直存活到最后一个引用触发回收回调。队列取出并不意味着可立即归还 Slot 或 mbuf；需要把该回调与实际资源释放绑定。即使消息持有 Cord，连续数组输出仍然要把字段内容写入最终数组；只有适配了别名输出的流及其寿命契约，才可以讨论跳过该次内容复制。[S3,S5]

### 3. 缓存尺寸序列化有前置条件

`SerializeWithCachedSizesToArray` 不是无条件更快的完整编码入口。先完成消息的所有修改，再对该实际消息调用 `ByteSizeLong()`，准备至少这么大的目标空间，然后序列化，且在两者之间不得修改消息。官方说明缓存尺寸序列化要求消息自上次尺寸计算后保持不变；违反条件的结果未定义。[S4]

复用线程局部消息不能省略每条内容变化后的尺寸计算，也不能仅计算一次嵌套消息大小后任意改字符串。测试应将 setter、尺寸计算和实际序列化分别报告，另给包含全部必要步骤的编码总成本。不要把尺寸计算挪到计时区外后声称测到了完整编码。

### 4. 嵌套线格式不意味着“绝不可能单遍编码”

嵌套消息使用长度定界的线格式，确实要求长度前缀先出现在相应内容之前；这限制了尚不知道子消息长度、又不允许任何预留/回填/暂存的严格正向流式写入。[S6]

但长度可以由已知字段长度直接算出，也可以反向写入、预留后回填，或采用具有明确规则的分块构造。官方 upb 编码源码明确采用反向编码，以避免预先计算长度。因此“嵌套 PB 天生不可单遍”是过度绝对化的断言。[S7]

这不表示自定义编码一定更快或更易维护。直接写线格式必须覆盖字段号、wire type（线格式类型）、varint（变长整数）、presence（字段存在性）、oneof、默认值、省略规则、长度溢出和容量检查，并与官方解码器互操作。普通生成式 PB 应保留为合法基线。

## DPDK 引用交接必须满足的条件

### 5. 引用计数不是固定成本，也不提供不可变性

DPDK v25.11 的 `rte_pktmbuf_refcnt_update()` 会遍历报文链的每个 segment（分段），更新各 mbuf 的引用计数；并非所有报文都是一次原子加法。底层是否使用原子计数还受构建配置影响，源码也包含引用计数为 1 时的专门路径。[S8]

共享引用交接至少应明确以下所有权规则：

1. 原持有者仍拥有有效报文时，先取得日志引用，再发布队列元素；不可先释放再补加引用。
2. 入队失败时撤销刚取得的日志引用，同时归还借用额度。
3. 原处理链与日志链各自恰好释放自己持有的引用。若采用独占所有权转移而非共享，则应作为另一种协议，不必机械增加引用。
4. 日志读取期间，其他参与者不得修改被借用的字节或相关链、偏移元数据。引用计数保证存储不会被过早回收，不等于字节不可变，也不是队列发布的内存同步协议。
5. 释放时机是最后一次实际使用完成，包括消息对象、外部 Cord、异步发送后端继续引用内容的情况；不是一律在出队时释放。

`rte_pktmbuf_free()` 会处理整条分段链，但仍有引用的段不会直接归还原池。最终回收还涉及间接 mbuf、外部缓冲区以及对应回收回调。不能把“logger 调了 free”直接等同于“所有这批存储现在都回到了 RX 池”。[S8,S9]

### 6. mbuf_base + offset 不总能直接读取字段

字段可能跨 segment；mbuf 元数据起点、数据起点与包内逻辑偏移不是同一个地址。必须明确 offset 相对于有效包数据，验证 `offset + length` 不溢出且落在包内，并处理分段跨度。

官方 `rte_pktmbuf_read()` 在范围连续时可返回原指针；跨段时会复制到调用者提供的临时缓冲区，超出报文范围则失败。因此 C 应覆盖连续/跨段两条路径，不能把全部输入都视为可直接连续读取。[S8]

如果 URL 等内容来自 TCP 重组缓冲区、解压缓冲区或解析器临时区，而非所引用 mbuf 的字节，单独保留这个 mbuf 无法保活那些地址。字段描述必须关联其真正的存储所有者。

### 7. 1024 槽降级不能保证池永不耗尽

槽位数量不能直接换算成固定的排队时间；它取决于到达速率、日志服务速率、批量刷新策略、字段大小和停顿。应实测 oldest age（最老元素年龄）与持有时间，而非把槽数称为固定毫秒数。

池容量同时受 RX 描述符、正常处理链、TX 未完成报文、解析/重组暂存、日志保留的分段以及各核缓存影响。日志队列水位只覆盖其中一部分；单条日志也未必恰好保留一个 mbuf。可使用下列资源账本检查配置，但每一项必须来自实际系统：

`RX 预留 + 正常流水线在途 + TX 在途 + 解析暂存 + 日志保留分段 + 核缓存 + 安全余量 ≤ 可用池容量`

降级为复制仅减少后续新增借用；之前借出的引用不会因此立刻释放。持续过载、其他处理链持有资源、超大分段包或回收错误都可能继续造成池压力。附件“仅凭 1024 槽阈值便百分百保证不耗尽”没有证明。[S8–S9]

更可实施的措施是：为日志借用设置独立的原子额度/分段预算，额度不足时在取得引用前选择复制或丢弃；观测真实可用池和保留分段；用有界队列、持有年龄与高低水位滞回来限制积压。它们是保护措施，不能在没有完整资源证明时宣传成绝对保证。观测池余量也不应取代并发正确的额度扣减。

## 建议的测量边界

1. **把核分工与编码器分开。** 至少分别标注 A/生成式 PB、B/生成式 PB、C/借用模拟+生成式 PB；如果新增直接线格式写入，再增加独立配置。schema、字段存在性、输入记录和变长内容保持一致。
2. **保留真实必要工作。** 核对每种方案是否计入字段提取、内容复制、setter、`ByteSizeLong()`、序列化、队列发布、批次装配和必要回收。分别列阶段成本及从输入到最终批次的总成本，避免把费用移动到计时边界外。
3. **并行性能不能只看单个函数。** 同时记录采集核和日志核占用、总核时间、接收与完成记录数、队列满丢弃、积压年龄、内存/分段保留量。逐核节省与系统总成本下降是两个不同问题。
4. **C 的模拟必须清楚标注。** 用普通内存块、原子引用计数或自建池实现的模型，只能证明该模型的交接行为；不能声称测到了真实 `rte_mbuf`、PMD（用户态网卡驱动）、RX/TX 描述符、DMA 或硬件网卡表现。真实 DPDK 验证还需检查实际构建、分段、NUMA（非统一内存访问）位置和池回收。
5. **没有混合工作负载就没有缓存干扰结论。** 热缓存编码微基准可以成立；要宣称解析工作因 PB 导致指令缓存污染，需在可复现的混合负载中验证。合成随机内存访问只能标为代理负载，不能改名为真实 DPI（深度报文检测）。无硬件计数器就如实说明，不为估计的缓存失效补上固定时间。
6. **队列和后端保持可比。** 同样的容量/丢弃策略/批次刷新条件、线程和物理核绑定、SMT（同时多线程）与 NUMA 情况、预热和重复方式均需报告。纯内存 BatchFrame 构建不代表跨机性能；应用中的大批次缓冲区也不自动等于一个可安全经普通 MTU 发送的 UDP 报文。
7. **先验结论不进入结果。** 附件的固定纳秒值、百分比、倍数和“绝不能采用 B”不应写入测试判据；先保留可互操作、可解释的三个基线，再根据实际采集核预算与总吞吐选择。
