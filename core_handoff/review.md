# Worker与日志线程分工基准独立审查

**后续核查修正（2026-10-29）：** 本轮3.21.12的`set_bytes(ptr,len)`会构造临时`std::string`，旧计时保留，但载荷复制账本须多计这一层；`mutable_bytes()->assign(...)`可避免它。详见[生成代码/API核查与重测](../stateful_handoff/PROTOBUF_3_21_NOTES.zh-CN.md)。


本审查只读源码、测试与测量记录，不运行性能、不修改实现。Worker指抓包/协议处理工作线程，logger指后台编码与发送线程。当前先建立核查标准，等作者源码就绪后追加实际结论。

## 用户参考文本中需要更正的结论

1. 官方C++ Protobuf普通字符串setter（字段设置接口）拥有数据，会复制字符串。把PB编码搬到后台线程只改变工作分配，不会自动消除该次复制。
2. 若A路径是 `source→IngressSlot→PB内部字符串→最终BatchFrame`，变长值共复制3次，Worker承担1次，logger承担2次。若B先编码到队列wire再拼batch，则是 `source→PB内部字符串→queued wire→BatchFrame`，也是3次，Worker承担2次，logger承担1次。
3. Bdirect若官方PB直接编码到最终可移交缓冲区、日志线程只传描述符/发送，才是2次。能否避免拼batch复制由最终缓冲区所有权与传输接口决定，不由“在Worker编码”这一条件自动决定。
4. C引用借用路径若logger仍用普通PB setter，则是 `mbuf字节→PB内部字符串→BatchFrame`，为2次复制。只有能够借用输入且直写最终输出的特定编码路径才可能只有1次；标准setter不能无成本借用任意mbuf字符串。
5. 嵌套PB需要长度前缀，但“不可能单遍编码”过于绝对。预先计算长度、倒序编码、预留并回填等都能处理，代价和复杂度不同。官方生成代码的具体路径应按实际API计时。
6. 参考中的10ns、45–80ns、3–5ns、3.5–6倍、L1污染70–100ns没有对应本轮测量，不能照搬。CPU缓存影响应通过实测差异和可用计数器解释，不能仅从“多调用几个函数”确定某级缓存失效量。
7. 队列1024项不天然等于1ms；等待时间取决于实际速率、服务时间、已有积压和停顿。高水位时改为copy可以减少新增借用，却不保证已有mbuf立刻归还，也不能解决队列已经满的问题。真实借用上限须保留接收池、描述符、分段报文和突发所需余量。

## 计量口径

- 两核流水线交付吞吐的倒数是整条流水线的墙钟间隔，不能作为Worker每条日志的CPU服务时间。双核容量通常受较慢阶段、跨核缓存一致性与队列策略共同限制。
- 饱和阻塞队列里的Worker线程CPU包含忙等。即使计算 `Worker CPU time / delivered events`，也不能把它命名为纯“填槽位/编码开销”。单线程无队列的服务时间基线与双核流水线需分别报告。
- Worker的DPDK轮询核本来就可能持续运行，100%核占用不等于日志消耗了全部CPU预算。日志对主业的机会成本须通过相同基础工作负载下的服务时间/吞吐变化评估。
- 统一批量循环外读取墙钟和线程CPU时钟；不要给每个10ns级事件调用一次clock。若采样排队延迟，须说明采样率、采样成本与未交付消息是否排除。
- 容量耗尽时spin（忙等）、drop（丢弃）、固定offered load（计划提供速率）三种实验不能混成一个指标。固定数量且队列满时等待的测试属于饱和背压吞吐，不是已验证无损的开放到达压测。
- 合成流表访问、哈希和内存访问可用于缓存/CPU压力敏感性测试，但不等于真实DPI（深度报文检测）、HTTP解析、ACL（访问控制规则）或DPDK抓包实测。

### 五条实际路径的复制账本

以下计数是每个非空变长数据字节的完整搬运次数，不是 `memcpy` 函数调用次数；一个HTTP记录的一次搬运可分成url/host/cookie三次调用。定长字段写入、队列元数据、4字节记录长度头仍有成本，未计入该“payload复制次数”。

| 实测模式 | Worker变长搬运 | logger变长搬运 | 总计 | 实际所有权与结果边界 |
|---|---:|---:|---:|---|
| A_native_slot | source→slot，1次 | slot→PB字符串→batch，2次 | 3 | 直接写最终队列槽位的原生记录 |
| A_scratch_then_slot | source→本地scratch→队列slot，2次 | slot→PB字符串→batch，2次 | 4 | 多了一次本地原生记录中转 |
| B_worker_pb_batch_copy | source→PB字符串→queued wire，2次 | queued wire→batch，1次 | 3 | Worker完成编码，logger继续聚合复制 |
| B_direct_worker_pb | source→PB字符串→queued wire，2次 | 0 | 2 | logger直接消费原wire，不聚合、不写batch记录长度头 |
| D_shared_pb_object | source→共享槽位PB字符串，1次 | 共享PB字符串→batch，1次 | 2 | 每槽位预创建PB对象，生产与消费阶段独占访问 |

本实现**没有C类型的真实 `rte_mbuf` 引用借用路径**。D共享PB对象拥有其字符串，不能称作“零拷贝借用mbuf”。它只适用于本实验的同进程C++线程间转移，不能把普通C++ PB对象指针直接传给另一台机器、Java或独立地址空间。

Bdirect相对B还省了4字节记录长度前缀和64KiB聚合缓冲区的写入/flush管理，因此是一个完整输出策略变体，不能把其全部收益归因于单独消除一次payload复制。其边界也没有实际NIC DMA完成、系统调用、网络发送或发送缓冲区异步回收。

### 正确的并发与对象复用行为

- 生产者先完成槽位数据和sequence/corpus_index写入，再release发布head；消费者acquire读取head。消费者完成序列化/复制/读取后release归还tail；生产者acquire读取tail再复用槽位。对当前单生产者单消费者结构，发布与归还关系完整。
- D模式的PB对象与字符串在槽位归还前只由logger读取，Worker等到相应tail进度后才再次写入，没有同时读写同一PB对象的主路径。它不证明PB对象本身支持无同步并发访问。
- 原生对象通过满足64字节对齐的存储建立生命期，并用 `std::launder` 获取视图；原生对象为可平凡销毁数据。源Packet语料在整个测量中不变且持续有效。
- `PBState` 预创建CommonHeader与HttpLog对象，`fill_pb` 每条覆盖所有业务字段，没有每条父 `Clear` 引起oneof子消息反复删除/重建。此实验始终是同一种HTTP日志，不覆盖真实多协议oneof切换与不同长度导致的容量扩张。
- 每条PB在字段更新后执行 `ByteSizeLong`，再用已更新的子消息缓存长度直写数组；检查输出容量和返回长度。没有把上一条的cached size当成本条大小。
- `Verify=true` 功能路径才执行PB Parse；正式性能路径的 `Verify=false` 不解析PB，只消费wire长度和首尾字节并设置编译器结果依赖。性能checksum不是完整正确性证明，完整核对来自独立功能路径。

### 测量与容量语义

- Worker绑CPU0，logger绑CPU1。每个保留trial至少0.3秒，外层5重复打乱80配置顺序；短于阈值的测量重新执行，并没有把未执行的迭代数写成结果。
- `batch=1/32` 是**队列发布与归还的批量**，不是一包内网络消息条数。64KiB聚合缓冲区是另一层，两者不能混为网络批量发送效果。
- 固定队列容量256的主矩阵覆盖64/256/1024B变长总量、两种PB结构与五模式；容量4096仅在256B补充。实际槽位大小1344B，所以两档环形存储336KiB与5.25MiB；D另有PB对象空间。`SpaceUsedLong` 是PB报告的对象空间，不是包含全部分配器元数据的精确常驻内存量（RSS）。
- 生产者以最快速度生成固定数量消息，队列满就忙等，完成后还等待最终drain（排空队列）。`dropped=0` 是这个背压实验的设计结果，**不是开放到达超负荷时没有丢包的证据**。当前没有独立的offered-rate、队列满丢弃或日志线程暂停实验。
- Worker总CPU从开始发布到最终drain结束，含队列满忙等和末尾等待；logger总CPU含空队列忙等。polls与stall episodes分别计数，但它们不是忙等持续时间，不能据此直接算出纯编码CPU。
- 双核墙钟区间包含最终logger消费完成，join发生在区间结束之后；不包含每次新建环形槽位、D对象池和预热PB字符串。此边界适合长期池化场景的稳态容量，不是冷启动或每条分配成本。
- 单线程服务时间由父任务单独测量，不能用双核 `elapsed/messages` 或包含spin的Worker CPU/messages替代。双核 `msg_per_s` 描述整条饱和流水线；logger慢时，Worker可以主要花在等待上。
- `run_dual.py` 对实际源码、生成PB源码、构建脚本与二进制保存前后SHA-256快照，并保留cgroup与进程资源使用记录；最终只有快照一致且完整结束的结果才应纳入汇总。

### 已知边界，不属于本次合法语料阻断

`extract` 和 `fill_slot` 是受信任语料辅助函数，依赖 `make_corpus` 的包尺寸、长度与≤1024B总尾部保证，没有校验任意外部报文、畸形长度和溢出；不能把它们作为可直接暴露给真实网络的解析接口。这里的source extraction是从已知偏移复制64B头和三个已定位切片，不是Ethernet/IP/HTTP协议解析。

当前双核代码没有合成流表/规则树负载，不能从这组双核结果推断真实DPI主业受到的缓存污染。若父任务另加单线程合成压力，其结果应继续命名为“合成缓存/访存工作负载敏感性”，不能代称真实抓包、DPI、ACL或真实网关端到端测量。

矩阵终结状态：数据等价、PB复用、SPSC所有权、可信范围内缓冲区边界、CPU计时与性能sink已静态核查；作者报告完整功能路径通过。开放到达/丢弃、真实mbuf引用、任意输入安全、并发多生产者与真实DPI不在此实现的验证范围，不能标为已通过。

### micro.cpp 的计时边界

- Worker五种stage（测量阶段）都从相同Packet提取SourceView，消费相同九个标量与总尾部长度，再分别仅提取、原生直写、本地scratch再复制、PB完整编码、填充共享PB对象。其差异是无队列条件下的本线程工作，不包含SPSC发布、跨核缓存一致性或队列满等待。
- logger四个stage分别测原生槽位→PB编码、已有PB对象序列化、已有wire复制、直接消费已有wire。它们的输入已预构造，不能把它们称为全链路成本。
- 预热后在整段循环外读取墙钟和线程CPU时钟，保留的trial至少80ms；五次重复随机顺序。没有给每个事件打时钟。结果消费和编译器内存依赖保留，输出指向独立缓冲区。
- 压力场景是**32MiB数组上的8次依赖读取**，下一次索引依赖上次读出的值，cursor跨调用延续；它并非真实哈希表、流状态机、HTTP解析或DPI，也没有测得L1/L2/L3 cache miss计数。由此观察到的变慢只能归为合成访存压力下的敏感性，不能凭空分配给某级缓存污染。
- 单线程语料和输出池均有4096项，包含4096个预热PB对象。这个工作集与主双核queue256的对象池不同；可以用于比较隔离工作策略，不能把其各stage时间精确相加后当成主矩阵的容量预测。
- 各stage包括同一测量框架的调用、分派与结果消费，且编译器可能对未使用的SourceView成员消除计算。减去extract基线可以展示近似增量，不能把差值宣传成独立、恒定的单次memcpy指令成本。

### drop_demo.cpp 的丢弃语义

- 这是嵌套HTTP、256B尾部、A/B/D三模式的定向演示：每个trial计划以250k/s执行50000次提供，共200ms计划区间；队列256/4096，logger起始sleep请求为0/10ms，各重复3次。它没有覆盖Bdirect/A_scratch或任意速率扫描。
- 队列满直接drop-new，不等待可用槽位，也不为该条填充PB/原生记录。成功发布的序号按accepted编号递增，源语料按offered编号取值，丢失不会造成SPSC接收序号伪错误。
- producer结束后release设置done；consumer在done acquire后再次读取head，避免依据旧head提前结束。最后join保证所有accepted数据已消费，校验 `offered = accepted + dropped`、`accepted = received`、观测水位不超过容量。
- 与前述饱和背压矩阵不同，这里真正实施满队列丢弃。代码仍执行全部50000个计划槽；若源线程落后，实际发送区间可以超过200ms。它报告最大source lateness与实际send/drain时长，所以250k/s是计划速率，不能无条件称为已保证的实际注入速率。max_queue是生产者观察到的水位，可能含其读取tail后consumer继续推进造成的保守差值。
- logger的sleep起止与实测 `pause_observed_ns` 是人为停顿，不是JVM GC（垃圾回收）实测。10ms×250k/s约2500个计划到达，能用于解释为何256与4096槽的行为不同，但调度抖动、恢复服务与生产迟到会影响实收数字，不能用理论差值替代原始计数。
- 此演示没有报告Worker服务CPU，也没有借用真实mbuf或观察网卡接收池。它支持“有限队列 + 显式丢弃 + 守恒计数”的行为说明，不是稳定微秒延迟、真实网络抗GC能力或接收池永不耗尽的证明。

双核最终运行记录已显示：400行、80配置各5重复，最短保留trial超过0.3秒、errors=0，源码/二进制前后哈希一致。`dual_run_timing.json` 记录正式运行返回0。结果中的反直觉排序（例如额外scratch复制有时更快、共享PB对象减少复制却可能更慢）不应被删除或用未测的缓存原因强行解释；以具体工作集、对象生命期、队列与CPU分配边界呈现即可。
