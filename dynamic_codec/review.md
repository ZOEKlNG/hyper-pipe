# 动态字段编解码基准独立审查

审查日期：2026-10-29。审查目标为 HybridTVTLV、ProtoEmitOp、官方 upb 和 GeneratedPB（官方生成的 C++ Protobuf）在**运行期挑选既有字段**时的正确性及测量公平性。本文不运行性能测试；源码和功能核查状态随实现就绪后更新。

## 先确定比较的问题

- **动态选字段**：消息结构与可用业务字段的全集已知，配置决定本条输出哪些字段。GeneratedPB 配合运行期掩码也能做到，无需每次重编译。
- **动态 Schema（消息结构定义）**：运行期加入新的字段编号、类型和结构。upb 的运行期消息表、手写计划解释器可支持某些此类变化，但上游如何提供新业务值、消费者如何识别其含义仍需另一层契约。不能把“从既有11个字段选子集”的结果扩展成“任意新类型无需适配”。
- **编码交付边界**：从同一个入口记录读取本条动态选择的字段，完成字段填充并产出可由组件独立持有的连续输出缓冲区。若库先写入 Arena（按批次释放的内存区），还应把复制到组件缓冲区的成本计入，或明确另列“移交库缓冲区所有权”的不同路径。
- **解码边界**应分别列出：①校验 + 别名视图（字符串/字节切片继续借用输入）；②校验 + 深拷贝（结果独立持有字节）。不能把 upb AliasString（字符串别名）与 GeneratedPB ParseFromArray 的内部拥有型结果混成一个无注释排名。
- 手写 ProtoEmitOp 可以生成某个标准 Protobuf 子集的合法字节；这不等于实现了通用 Protobuf 的全部类型、重复字段、合并语义、未知组字段、反射与演进规则。

## 用户参考文本中不能照搬的内容

1. 示例 Hybrid u64 解码分支使用 `reinterpret_cast<const uint32_t*>`，把64位值读成32位；同时该写法有未对齐访问和 C++ 类型别名规则风险。应通过 `memcpy` 等合法方式完整读取64位并规定字节序。
2. `static_cast<uint16_t>(sv.size())` 会将65536及以上长度截断；必须先验证长度范围和输出容量。
3. `type == 3` 被 `else` 当作 bytes；该保留类型的跳过规则没有定义，应拒绝或定义明确扩展格式。
4. 示例没有输出容量参数，使用本机字节序，不能当作跨语言可上线协议。`p + n > end` 还应改为剩余长度比较，以避免无效指针运算。
5. 示例 upb 编码 Arena 释放后继续使用 `wire_buf`，并把同一个 scratch 内存区用于解码 Arena，会使编码结果失效或被覆盖。必须在释放前复制结果，或明确延长拥有者的生命期并使用独立解码存储。
6. 13.5ns、19.2ns、27.5ns 等数字在参考中没有可检查的实测记录，不能写入本轮实测结果。Varint（变长整数编码）也不天然导致分支预测失败；成本需要由真实数据分布、编译器与运行环境测量。
7. 该例的“6个64位 + 4个32位 + 160B尾部”数据值总长是224B；不能把此配置直接称为256B编码后消息。输出字节数应从每个编码器实测。

## 正确性核查矩阵

下表是各实现都应对照的核查要求。`待查` 表示尚未取得对应源码/测试结果，不表示通过。

| 类别 | 输入/操作 | 预期与核查点 | 状态 |
|---|---|---|---|
| 数值边界 | 0、1、127、128、255、256、UINT32_MAX、UINT64_MAX，及高32位非零 | 全部所选字段逐值比对；64位不能截断；固定宽度字节序一致 | 待查 |
| 默认值存在性 | 所选字段显式为0；字段未选；bytes存在且长度0 | 明确 presence（存在性）契约。若采用隐式默认值，区分语义相等与字节/存在性相等；不要让某方案多发零字段而不说明 | 待查 |
| 字段缺失 | full→sparse→none→full；同一输出对象/消息复用 | 未选字段不得残留上一条值、存在位或尾部切片；清理工作应在相应计时边界内 | 待查 |
| 动态计划 | 4/8/11字段、随机顺序、运行期更换计划、空计划 | 选字段逻辑不得被编译期常量完全折叠；计划构建、查表、分支与切换的计时边界一致 | 待查 |
| 新字段/未知字段 | 已知 wire type（线上字段类型）的未知编号 | 能按协议跳过且不越界；PB 用官方库交叉解码，TLV 用独立规范/黄金字节核对 | 待查 |
| 类型编号 | TLV保留type3；PB非法wire6/7；PB field0 | 明确拒绝；不能把未知类型当已知bytes；PB合法组字段若不支持应声明子集限制 | 待查 |
| 不匹配类型 | 已知字段编号携带不同合法PB wire type | 与官方库行为对照；若有意更严格，标为受限解析器 | 待查 |
| 重复字段 | 同一标量/bytes重复出现 | PB通常最后一个值生效；TLV应明确定义。不能隐含 first-wins/last-wins 差异 | 待查 |
| 截断 | 每个合法输出的所有字节前缀、单字节tag、缺少长度/值 | 仅完整合法消息应通过；空消息是否有效按协议定义；失败不得发布半成品结果 | 待查 |
| 长度边界 | 0、127、128、255、256、65535、65536 | Hybrid ≤65535正确；65536明确失败，不能截断。PB大长度按其自己的协议能力报告，不能伪称TLV同能力 | 待查 |
| 非法长度 | 长度大于剩余输入、超大/未终止PB长度varint、整数溢出 | 剩余长度比较安全，长度加法不溢出，限定最多读取字节数 | 待查 |
| 输出边界 | 精确容量、容量少1、零容量；前后哨兵字节 | 不越界，失败的输出长度/错误码明确；大小计算与实际写入一致 | 待查 |
| 别名结果生命期 | 解码后读取/修改输入；输入仍有效时检查指针范围 | 借用视图不得越过输入生命期；AliasString只是允许别名，不能未经核实宣称所有路径都必然别名 | 待查 |
| 深拷贝结果生命期 | 解码后修改/复用原始wire缓冲区 | 已拥有的解码结果不变；Arena释放前完成消费或移交；禁止编码与解码Arena覆盖同一有效输入 | 待查 |
| 计划生命期 | plan-switch时旧消息/旧缓冲区仍在途 | 热更新只更换不可变计划引用；旧计划/结构定义须活到相关读取结束；单线程切换不等于并发安全已验证 | 待查 |
| PB交互兼容 | EmitOp→GeneratedPB/upb；GeneratedPB/upb→手写解析 | 按值与存在性比较，不能只要求自编码器与自解码器互相通过；字段顺序差异不应被当成失败 | 待查 |

## 公平性核查清单

1. 所有方案使用相同业务值、相同字段选择、相同尾部内容与长度，逐条报告真实输出字节数。数据至少跨一批记录变化，并检查所有选中数值与尾部，避免只读一个字段或恒定输入被优化。
2. 主编码指标应包含本条记录到消息的字段填充、配置遍历/分派、实际编码以及最终输出复制。预构建 Message 仅 Serialize 的结果应另列，不能作为动态编码总成本。
3. 上游 bytes 已在入口记录中：直接写wire的一次复制与先填拥有型PB对象再编码的两次复制，是架构差异，应记录复制语义，不应藏在未计时预处理里。若 upb SetString 借用入口切片，应保证入口在整个编码期间有效。
4. 接收方比较区分别名视图和拥有型结果；边界校验开启与否、未知字段处理和实际消费字段数量一致。不要把“读一个id”与“完整解析所有字段 + 拷贝160B”作为同一解码指标。
5. 每次 Arena/Message 的创建、复用、重置、释放必须说明并纳入对应运行期成本；4KiB预留块是否发生堆回退要有证据，不能仅凭设置一个scratch数组宣称零分配。
6. 对象复用必须清除缺失字段；库对象的容量复用可以保留，但不能保留上一条的语义值。热路径与冷路径（计划/消息表构建）的时间分别报告。
7. 所有正确性测试必须在性能测试前通过；测试与真实性能路径应使用同一实现。性能隔离由父任务统一调度，本审查不运行性能。

## 源码审查与功能测试记录

待实现代理提交文件后分批追加。轻量功能测试须先征得该文件作者同意；不会修改其他代理负责的源码。

### 首轮静态审查（实现仍在迭代）

已读 `common.hpp`、`plan_compiler.hpp`、`pb_adapters.hpp`、`custom/codecs.hpp`、`upb/adapter.hpp` 与 `upb/adapter.cpp`。

- 当前实际字段全集是 **5个u64 + 4个u32 + 1个bytes，共10字段**，不是参考文本的11字段。计划配置是 full（10字段）、subset（id/seq/type/payload共4字段）、no_payload（9字段）。值区长度是56B加payload；编码后长度需另外实测。
- `plan_compiler.hpp` 从受控字段注册表生成offset和类型，不允许JSON配置任意内存偏移；拒绝未知键、未知字段、重复字段及冲突fid/type。配置支持选择与重排既有字段；没有通过该配置添加业务全集以外的新字段。
- `GeneratedPB::encode` 的 `Clear + set + SerializeToString` 在同一调用内，输出string拥有结果，保留容量复用。`ReflectionPB` 确实通过官方 `DescriptorPool::BuildFile`、`DynamicMessageFactory` 创建运行期结构定义，查找字段缓存发生在初始化；编码填充和反射分派仍在计时函数内。
- 当前各方案采用proto3隐式默认值语义：0与empty可不在线上出现，缺失读取为0/empty。选择了值为0的字段和未选择字段没有独立线上存在位。若业务需要区分两者，须另测显式presence方案，不能把本轮结果作为其性能。
- `common.hpp` 的无序求和与payload长度/首尾字节消费足以形成性能测试的结果依赖，**不构成完整正确性证明**。字段互换或payload中部损坏仍可能得到相同checksum；已请作者功能测试逐字段和完整payload核对。
- 自定义实现使用明确的小端字节序，通过剩余字节数做边界检查，64位读写完整，拒绝保留type3及超过65535的Hybrid payload；初步未见参考示例的越界/截断问题。输出接口是自行扩展的 `std::string`，并非调用者给定容量的span；“容量少1”测试不适用于该API，应核查大小上界和用内存检查工具排查越界。
- 自定义 Protobuf view（借用输入的读取视图）目前既接受已知u64的wire0又接受wire1，u32既接受wire0又接受wire5；这与某一个具体官方Schema对错误wire字段的处理不同。它还主动拒绝u32溢出与组字段。作为主基准合法输入的受限读取器可以测，但不能宣称是通用PB解析替代。已反馈作者修订或明确限制。
- 自定义编码器预先把输出string扩到保守上界，写后缩短；扩展时可能发生清零和容量调整，这些成本留在主编码指标中。不能把结果宣传成手写理论最优上限。
- upb 的主编码调用包含 Arena初始化、Message创建、字段填充、`upb_Encode` 与最终 `out.assign`；最后复制发生在Arena析构前。解码也在Arena释放前消费结果，且输入wire与scratch分离，生命期边界初步正确。
- upb 的预分配模式使用64KiB Arena与空回退分配器；适配器对输入payload设8192B限额。这是本适配器/实验路径的上界，不是upb或Protobuf协议的最大长度。借用入口payload与先复制入口payload两种编码路径应分别标注，最终owned输出并不强制要求中间输入也深拷贝。
- 所有Codec实例都含可变状态（PB复用消息、upb scratch等）时，单线程调用可用；本轮没有证明同一实例并发调用、并发配置更新或在途旧Schema销毁安全。

初步结论：主合法输入路径暂未见阻止继续功能核查的内存错误；不能在功能测试日志就绪前标记矩阵全通过，也不能把受限解析器的成绩解释成通用库完全等价成绩。
