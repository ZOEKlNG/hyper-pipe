# 同机 Linux loopback 传输实测

2026-10-21 在本任务 VM 上测量。正式基线 75 个吞吐 trial、45 个 RTT trial，另做 12 个 paced UDP trial。发送应用线程绑 CPU1，接收线程绑 CPU2；ZeroMQ 另有未绑核的 I/O 线程。libzmq 4.3.5，C++20/GCC14.2，`-O3 -DNDEBUG`。完整方法与复现命令见 README.md，所有 trial 见 results_*.csv。

**这些是同机 loopback 测量，不能当作双机 NIC、DPDK 或 Flink 的实测。** body 长度已经包含 8 字节序号，TCP 每条另加 4 字节长度头。没有编解码工作。CPU 是整个发送与接收进程合计。

## 饱和交付吞吐

每组合先独立 warmup 100ms，再测 5 次，每次发送 600ms；下表为实收速率中位数，单位百万条/秒。

| body 总长 | TCP 单条写 | TCP 每次写32条 | UDP 单条 | UDP mmsg32 | ZeroMQ PUSH/PULL TCP |
|---:|---:|---:|---:|---:|---:|
| 64B | 0.342 | 6.477 | 0.378 | 0.525 | 1.991 |
| 256B | 0.204 | 2.986 | 0.379 | 0.381 | 1.252 |
| 1024B | 0.303 | 1.346 | 0.289 | 0.336 | 0.409 |

256B 时相应进程 CPU 平均占用中位数为 1.54、1.43、1.24、1.37、1.51 个核。不能将这些两端合计结果称为“单核上限”。正式所有 trial 的 sent/received 一致、序号无间断，UDP 也没有观察到 accepted 之后的丢失；这表示当前负载生成方式先受到发送处理能力限制，不表示接收可承受任意速率。

跨 trial 波动明显，例如 TCP256B batch32 为 2.745–5.781 M/s，ZeroMQ256B 为 0.815–1.907 M/s。使用中位数并保留原始值；无独占物理机、频率锁定或邻居负载隔离。CPU cgroup 的 nr_throttled 在基线和 paced 两阶段都保持 4，没有新增 quota throttling，但这不能排除宿主调度等 VM 干扰。

TCP batch32 将多个独立帧合并成一次写；UDP mmsg32 仍然是32个独立 datagram。两者不能视作同一个“批量”优化。TCP loopback 也可能受大 MTU、内核聚合等影响，不能把所得差距直接外推到物理 Ethernet。ZeroMQ 使用真实 libzmq 的 copying `zmq_send`，并未穷尽其零拷贝消息 API 和全部调参。

## 轻载 RTT

每次1000次预热、5000次测量、5个重复；每个时刻只有一个请求在途。256B 的“每次重复内部 p50/p99，再取5次中位数”为：

| 方案 | p50 RTT | p99 RTT |
|---|---:|---:|
| TCP | 27.97 µs | 50.42 µs |
| UDP | 15.29 µs | 39.62 µs |
| ZeroMQ REQ/REP | 36.84 µs | 75.78 µs |

全部 RTT timeout 为0。这里测的是应用观察的往返时间；不能除以2宣称真实单向延迟，也不能代表负载下 p99。

## UDP 256B 的固定计划到达测试

固定一秒的计划窗口，每个目标速率重复3次。发送者按原始计划时间 busy-spin，非阻塞调用 send；接收数据携带 planned 和 actual-send 时间。窗口结束仍未执行的计划槽记为 source_schedule_missed，不将它伪装成已发出的网络包。

| 计划条/秒 | 实收条/秒中位数 | 生成器未执行槽比例 | planned→arrival p99 | actual-send→arrival p99 | sender lateness p99 |
|---:|---:|---:|---:|---:|---:|
| 50,000 | 50,000 | 0% | 40.55 µs | 25.04 µs | 13.26 µs |
| 200,000 | 200,000 | 0% | 306.91 µs | 32.05 µs | 286.03 µs |
| 500,000 | 295,982 | 40.8032% | 402.516 ms | 28.02 µs | 402.508 ms |
| 1,000,000 | 292,738 | 70.7261% | 700.636 ms | 28.74 µs | 700.632 ms |

**延迟分位数排除了未生成/丢弃记录，必须连同完整计数阅读。** 所有 accepted 的 datagram 均收到；500k 与1M目标并没有真正完整注入内核，不能用这些 trial 声称接收端承受了1M/s且无丢失。高 planned 延迟主要来自源发送循环追赶欠下的计划槽，不是网络排队。目标速率和实际供给速率必须分开报告。

## 可支持的结论

1. 一次写一条的 TCP 不能代表已经充分批量的 TCP；本工作负载下，批量收益比更换某个上层 API 更显著。
2. 自己写 UDP 不会自动超过已有组件；在本 VM 中，单线程逐报文 syscall/内核发送先成为瓶颈，mmsg 也未保证所有尺寸都有数量级收益。
3. 轻载 RTT 良好不代表开放负载下计划到达延迟良好。生产压测应同时报告 offered、accepted、received、source generation misses、接收缺失和发送 lateness。
4. 需要双机真实硬件、相同完整事件布局、相同可靠性语义、实际 Java/Flink source 与处理链继续测量后，才能做生产容量决策。
